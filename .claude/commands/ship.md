## Context
The user frequently wants to commit and push in a single command. This skill handles the full git ship workflow: stage, commit with a good message, and push.

## Your Task

Ship the current changes: commit and push to remote.

### Steps

1. Run in parallel:
   - `git status` (never use `-uall`)
   - `git diff` + `git diff --cached` to see all changes
   - `git log --oneline -5` for commit message style

2. Analyze all changes and draft a concise commit message:
   - Summarize the nature (feat, fix, docs, refactor, etc.)
   - Focus on "why" not "what"
   - Do NOT commit files that contain secrets (.env, credentials)

3. Stage relevant files (prefer specific files over `git add .`), then commit:
   ```
   git commit -m "$(cat <<'EOF'
   <message>

   Co-Authored-By: Claude Opus 4.6 <noreply@anthropic.com>
   EOF
   )"
   ```

4. **Pre-push sanity check (mandatory)** — before pushing, verify the local repo and remote actually share history:
   ```bash
   # a) Confirm we're in the repo we think we're in
   git rev-parse --show-toplevel
   git remote -v

   # b) Fetch the target branch
   BRANCH=$(git rev-parse --abbrev-ref HEAD)
   git fetch origin "$BRANCH" 2>&1
   ```
   Then check divergence shape:
   - **If `origin/$BRANCH` doesn't exist on the remote** → safe to push (`git push -u origin $BRANCH`).
   - **If local is fast-forward of `origin/$BRANCH`** (`git merge-base --is-ancestor origin/$BRANCH HEAD`) → safe to push.
   - **If `origin/$BRANCH` is fast-forward of local** (remote ahead, no local commits) → nothing to push.
   - **If local and remote have diverged but share a common ancestor** → standard case; do `git pull --rebase` then push.
   - **If local and remote share NO common ancestor** (`git merge-base origin/$BRANCH HEAD` returns empty / fails) → **STOP**. This means disjoint root histories. Do NOT push, do NOT force, do NOT rebase. Report the situation to the user with branch SHAs and a note that pushing would require either (a) abandoning local work, (b) abandoning remote work, or (c) pushing local as a new branch via `git push origin <local-branch>:refs/heads/<new-branch-name>`. Wait for user direction.
   - **If a `--force` push would be needed** → STOP and require explicit user confirmation that includes the word "force". Default refusal is correct.

5. Push to remote. Use `git push -u origin <branch>` for new branches; plain `git push` otherwise. If rejected (remote ahead despite the check), do `git pull --rebase` first, then push.

6. Report the commit hash, the branch pushed, and confirm push succeeded.

### Guardrails
- Never use `--force` or `--no-verify`. If forcing seems necessary, stop and ask the user — they must say "force" explicitly.
- Never amend unless explicitly asked.
- **Pre-push divergence check is mandatory** — if local and remote share no common ancestor, pushing risks destroying remote work. Stop and ask before doing anything.
- If push fails after rebase due to conflicts, stop and inform the user.
- Never commit .env files or credentials.
- **If the working directory isn't actually a git repo** (no `.git` and parent repo's `.gitignore` excludes the path) — stop and ask whether to `git init` here or commit in a different repo. Don't silently commit to the parent repo.

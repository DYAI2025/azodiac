## Context

After a PR has been merged (or is about to be), a code review surfaces findings categorized Critical / Important / Minor. The "Important" findings deserve action but shouldn't reopen the original PR — they belong in a small focused follow-up PR.

The user does this cycle frequently: `/code-reviewer` → categorized findings → `/writing-plans` with the findings → subagent execute → `/ship`. This skill chains those steps but **keeps the user in the loop at the decision points** (which findings to fix, plan-approval before execution).

The skill is opinionated about scope: only **Critical** + **Important** findings become tasks. **Minor** findings are reported but not actioned (they bloat the fix-plan and dilute the focused-PR principle).

## Your Task

Run an end-to-end review-and-fix cycle on a PR or branch range, producing a separate follow-up PR with the fixes.

### Steps

1. **Determine review scope**
   Ask the user (via AskUserQuestion) what to review:
   - A specific PR number (use `gh pr view <N>` to get commits + diff)
   - A merged PR by number (same)
   - The current branch vs main (`git log main..HEAD --oneline`)
   - A specific commit range

2. **Run the code review**
   Invoke the `code-reviewer` skill on the scoped diff. Capture findings.

3. **Present categorized findings to the user**
   Group findings:
   - **Critical** — blocking issues. Listed first.
   - **Important** — defensive/hygiene issues that warrant a fix-PR.
   - **Minor** — reported but NOT actioned (state this explicitly).

   If there are no Critical or Important findings, say so and stop — there's nothing to fix.

4. **Get user approval on which findings to action**
   Use AskUserQuestion to confirm the user wants to proceed with the Critical+Important set, or wants to drop some. The user might:
   - Approve all → proceed
   - Drop one finding → proceed with the rest
   - Cancel entirely → stop the skill

5. **Create a branch and write the fix-plan**
   - Branch: `YYYY-MM-DD-<short-feature-name>-fixes` off main
   - Use `writing-plans` skill to produce `docs/plans/YYYY-MM-DD-<short-feature-name>-fixes.md`
   - One TDD-style task per finding, smallest possible scope
   - Frequent commit pattern (test → fix → commit)
   - Explicitly drop Minor findings from the plan with a one-line note explaining why

6. **Execute the plan via subagent-driven development**
   - For each task: dispatch a fresh subagent that follows the plan exactly
   - **Critical instruction to subagents**: halt-on-defect. If a RED test passes on first run, the test isn't reaching the code path under test → STOP and report, don't proceed.
   - Review subagent output between tasks — if it caught a plan defect, surface it to the user before continuing.

7. **Ship the fix-PR**
   - Run full test suite, confirm green
   - `git push -u origin <branch>`
   - `gh pr create` with title `fix(<scope>): <topic> (PR-<N> follow-up)` and body summarizing which findings are addressed (with finding IDs from the review) and which Minor findings were intentionally dropped

### Guardrails

- **Critical/Important only.** Minor findings are noise in a follow-up PR. Mention them in the PR body for traceability, don't fix them in this cycle.
- **Subagent halt-on-defect is non-negotiable.** If a subagent reports a plan defect (RED test passes, or assertion isn't reachable), stop the cycle and surface to the user. Do NOT have the subagent "fix the plan and continue" — plan defects are user-decision territory.
- **One commit per finding.** Don't bundle multiple findings into one commit, even if they touch the same file. Reviewer of the follow-up PR should see one finding = one commit.
- **Original PR is never reopened.** This cycle produces a separate PR. If the original PR isn't merged yet and the user wants the fixes in it, they have to do that manually (it's a different mental model).
- **Always show RED → GREEN evidence in commit messages** for TDD-style fixes. The follow-up PR's review value is largely "the test catches the regression now."

### What this skill is NOT

- Not a one-shot fix-and-push. There's a user-approval checkpoint after the review (step 4).
- Not a replacement for `/code-reviewer` or `/writing-plans` standalone — those still work alone. This skill is the orchestrator when the user explicitly wants the full cycle.
- Not for fixing Critical findings in an already-merged production-broken PR. That's a hotfix scenario — use `/SDLC-fix` or just a direct fix-and-PR.

## Context

Before starting a sprint, perform a systematic gap analysis of the current code state, apply ultrathink-craftsmanship reasoning to identify real vs. noise gaps, then produce two artifacts: a bite-sized implementation plan and a goal document.

This skill combines `/ultrathink-craftsmanship` reasoning with `/writing-plans` output format. Run it at sprint boundaries, not mid-sprint.

## Your Task

Produce a sprint plan at `docs/plans/YYYY-MM-DD-<sprint-name>.md` and a goal document at `docs/goals/GOAL-<feature>.md`.

### Steps

**1. Read current code state (parallel)**

Read all key files relevant to the area being analyzed. For each layer, read in parallel:
- Backend: `main.py`, `models.py`, all store/service modules
- Frontend: context files, service files, component files relevant to the feature
- Config: `railway.toml`, CI workflows, `CLAUDE.md`

**2. Run both test suites**

```bash
# Backend — always use uv run, never bare python
uv run python -m pytest backend/tests/ -v 2>&1 | tail -20

# Frontend
npm run test:run 2>&1 | tail -15
```

Record: exact pass/fail counts, any timeout or error messages verbatim.

**3. Apply ultrathink-craftsmanship gap analysis**

Output triage line first:
```
Triage: [Hotfix|Standard|Tief] — Verb: gap-analyse — Engpass: [one sentence] — Modus: [voll|kurz]
```

Then for each gap found, classify:
- **CRITICAL** — blocks CI or core flow
- **HIGH** — functional correctness issue users will hit
- **MEDIUM** — reliability, privacy, correctness edge case
- **LOW** — hygiene, documentation

For CRITICAL/HIGH gaps: apply Phase 2–4 of ultrathink (options table, counter-check, failure mode chain).

Produce a gap table:

| ID | Severity | Description | Root cause (1 sentence) |
|---|---|---|---|

**4. Apply gegenprüfung (required)**

For the top 2–3 gaps:
- Stärkstes Gegenargument
- Failure Mode Chain: "Wenn A schiefgeht, dann B, dann C"
- Bias check: is the "obvious fix" actually correct, or is it the familiar tool?

**5. Write sprint plan**

Save to `docs/plans/YYYY-MM-DD-<sprint-name>.md`.

Plan header:
```markdown
# [Sprint Name] Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** [one sentence]
**Architecture:** [2–3 sentences]
**Tech Stack:** [table or list]

---
```

Each task must follow `/writing-plans` granularity:
- Exact file paths (Create/Modify/Test)
- Failing test first, then implementation, then verify green
- Exact bash commands with expected output
- Commit at end of each task

Guardrail from this project: backend tests always use `uv run python -m pytest`, never bare `python`.

**6. Write goal document**

Save to `docs/goals/GOAL-<feature>.md`.

Goal document structure:
```markdown
# Goal: [Feature Name]

**Status:** In progress — [Sprint Name] open
**Owner:** [from git config or CLAUDE.md]
**Last updated:** YYYY-MM-DD

## What success looks like
[2–4 sentences — observable user outcome, not code]

## Architecture
[ASCII diagram or bullet list of data flow]

## Tech stack
[Table]

## Out of scope for MVP
[Bullet list]

## Gap analysis (as of YYYY-MM-DD)
[Gap table from Step 3]

## Constraints (non-negotiable)
[From CLAUDE.md or domain rules]

## Sprint history
[Table: sprint name, goal, status]

## Definition of done
[Checkbox list — observable, testable, not "code written"]
```

**7. Commit plan + goal docs**

```bash
git add docs/plans/ docs/goals/
git commit -m "docs: add [sprint name] plan and goal document"
git push
```

### Guardrails

- **Never skip the test run.** Current pass/fail state is ground truth — don't assume CI is green.
- **Backend tests: `uv run python -m pytest`** — bare `python` picks wrong interpreter.
- **Gap table before plan.** Don't write tasks for gaps that don't exist; don't skip gaps that do.
- **Ultrathink triage is mandatory.** Classify each gap; don't write a plan for `Hotfix`-level gaps.
- **Goal document is persistent.** Update it, don't duplicate it. If `docs/goals/GOAL-<feature>.md` exists, update it rather than creating a new file.
- **Plan is a dev brief, not a diary.** Include exact code, not "add validation here". Include exact commands, not "run the tests".

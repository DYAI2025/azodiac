## Context
Safely replace a term, variable name, or string across an entire codebase. Handles the common pitfalls: code-internal vs user-facing, partial matches, file types, and build verification.

## Your Task

Bulk replace term A with term B across the project.

### Steps

1. **Clarify scope** — ask if not obvious:
   - **User-facing only** (UI text, labels, titles) — leave code internals untouched
   - **Code-internal only** (variable names, class names) — leave user-facing text
   - **Everything** (both code and content)
   - **Specific file types** (e.g. only `.tsx`, only `.css`, only `.md`)

2. **Dry run — count occurrences:**
   ```
   Grep for the term across the project
   Report: X occurrences in Y files
   Show file list with counts
   ```
   Present the list and ask for confirmation before proceeding.

3. **Check for partial match risks:**
   - Would replacing "Ring" also break "String", "Rendering", "bring"?
   - If yes, use word-boundary-aware replacement or case-sensitive matching
   - Flag risky files and ask before touching them

4. **Execute replacement:**
   - Use `Edit` tool with `replace_all: true` per file for tracked replacements
   - For large batches (50+ files), use `sed -i` via Bash for speed
   - Skip `node_modules/`, `dist/`, `.git/`, lock files

5. **Verify build:**
   ```bash
   npm run build  # or project's build command
   ```
   - If build fails, the replacement broke something — diagnose and fix
   - Common: import paths, CSS class names, JSON keys

6. **Report:**
   ```
   Replaced "X" → "Y"
   Files changed: N
   Occurrences: M
   Build: PASS/FAIL
   ```

7. **Do NOT auto-commit** — let the user review the diff first with `git diff --stat`

### Guardrails
- Never replace inside node_modules, dist, or .git
- Never replace inside lock files (package-lock.json, yarn.lock)
- Always do a dry-run count first and show to user
- Watch for partial matches (substring collisions)
- Preserve case when replacing (e.g. "Ring" → "Signatur", "ring" → "signatur") if user wants case-matching
- If >500 occurrences, warn user and ask for confirmation before proceeding

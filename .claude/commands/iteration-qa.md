## Context

After completing an iteration (e.g. I0..I9 from a multi-iteration master plan), the user manually composes a QA review document under `docs/qa/<YYYY-MM-DD>-i{N}-<topic>.md`. The same structure is repeated every iteration: Iterationsziel → Testcommands → Browser/Viewport → Screenshots → Implementierte Änderungen → Architektur-Highlights → Code Review → Findings → Finaler Status.

This skill mechanizes the write-up: it scrapes git diff for the file table, runs the test commands, captures the latest screenshot dir, and renders the iteration template with the gathered evidence. The user then reviews + amends + commits.

## Your Task

Generate a complete iteration QA review document for a finished iteration. Reuses the project's existing template if present at `docs/qa/templates/iteration-review-template.md`; otherwise emits a sensible default structure.

### Steps

1. **Determine iteration scope** via AskUserQuestion:
   - **Iteration ID** (e.g. `I7`)
   - **Topic slug** (e.g. `navigation`)
   - **Commit range** — last N commits OR explicit range (`<sha>..HEAD`). Suggest `git log --oneline -10` to help the user pick.

2. **Gather evidence** in parallel:
   - `git log --oneline <range>` — commits in scope
   - `git diff --stat <range>` — files changed
   - `git diff <range> -- docs/qa/ test/ 2>&1 | head -200` — high-signal changes
   - Run `npm test 2>&1 | tail -8` and capture pass/fail/skip counts
   - If Playwright config exists, run `APP_BASE_URL=http://127.0.0.1:4100 npx playwright test --config=playwright.config.mjs 2>&1 | tail -5` (ask user about port first)
   - List screenshots in `docs/qa/screenshots/<iteration-slug>/` if dir exists

3. **Read the template** if present at `docs/qa/templates/iteration-review-template.md`. Fall back to a minimal template if absent:

   ```markdown
   # <ITERATION>: <Topic> — QA Review

   **Date:** <YYYY-MM-DD>
   **Iteration:** <ITERATION>
   **Status:** PASS

   ---

   ## Iterationsziel
   <one paragraph>

   ## Testcommands
   ```bash
   npm test
   # → <X/Y/Z pass/fail/skip>

   APP_BASE_URL=http://127.0.0.1:<PORT> npx playwright test --config=playwright.config.mjs
   # → <N passed>
   ```

   ## Browser / Viewport
   - Chromium (Playwright default)
   - Server: PORT=<PORT> node server.js

   ## Screenshots
   <table from screenshots dir>

   ## Implementierte Änderungen
   <table from git diff --stat: file | art>

   ## Architektur-Highlights
   <2-4 bullets summarizing the design decisions in this iteration>

   ## Code Review
   <constraint check + REQ-coverage>

   ## Findings
   Keine Critical/Major Findings.
   **Minor (gelöst):** <if any>
   **Minor (deferred):** <if any>

   ## Finaler Status: PASS
   ```

4. **Render the QA doc** by filling each section from the gathered evidence:
   - **Date** = today
   - **Testcommands** = real outputs from step 2
   - **Implementierte Änderungen table**: one row per file from `git diff --stat`, with a short "art" column (extract intent from commit subject lines)
   - **Screenshots table**: one row per file in the screenshots dir
   - **Architektur-Highlights**: ask the user for 2-4 bullets OR scan the commit body messages for design rationale

5. **Write to** `docs/qa/<YYYY-MM-DD>-<iteration>-<topic>.md`.

6. **Report and stop** — do NOT commit. The user reviews + amends the rendered doc, then commits manually (or via `/ship`).

### Guardrails

- **Never invent test results.** If a command fails to run, leave the section as `<TBD: run manually>` rather than fabricating output.
- **Never mark status PASS automatically.** Default to `DRAFT` until the user confirms.
- **Don't include screenshots that don't exist on disk** — only list what `ls` returns.
- **Don't run destructive commands** (no `git reset`, no `rm`).
- If the screenshot dir is empty or missing, surface this as a finding ("Screenshot evidence missing — Playwright run required").

### Variants

If the user already has a draft QA doc and wants to refresh the evidence sections only (testcommands, screenshots, file table), accept `--refresh <path>` and rewrite only those sections, preserving the user's prose in Architektur-Highlights + Findings.
